## Key decisions and rationale

**Only the vintage dimension is revised by the page-stated vintage (WI-2).** The
obvious implementation — re-run `scoreMatch` against the page with
`statedVintage` set — silently downgrades producer to `mismatch` for every
retailer whose product slugs are opaque ids (`/products/details/1557135`), because
the second scoring pass sees only the URL. Producer, denomination and bottling
keep their Step 1 verdicts, which were judged against the full title, snippet and
URL. The same reasoning drives `confirm-retailer-link`: the developer found that
exact page by hand, which is stronger evidence of identity than any text match, so
producer and denomination are recorded as confirmed while bottling and vintage are
still judged.

**`vintage_mismatch` keeps its meaning; `vintage_verdict` is added alongside it.**
The spec noted the old computation fails open — `matched_vintage !== null && …`
means an unstated year counted as agreement. Making `unknown` count as a mismatch
would have been the literal reading, but `vintage_mismatch` also gates the price
stats, so that would have quietly excluded a lot of real listings from
`price_min/avg/max` — a product decision, not a bug fix. Instead the third state
is now representable and visible, and the stats keep their existing shape.
**Flagged for the developer.**

**Pass 1/Pass 2 merge deduplicates by consumed Serper item, not by slug (WI-6).**
A configured retailer's slug comes from `RETAILER_CONFIG` (`benchmark`) while the
fallback slug is derived from Serper's merchant string
(`benchmark-wine-group`), so slug comparison alone lets one shop through twice
under two names. Caught by a test written for it.

**Cross-feeding uses merchant *names*, not domains, in the price → reviews
direction (WI-7).** Serper's Shopping response carries a merchant display name
and a `google.com/search?ibp=oshop` aggregator link — never the merchant's own
domain — so there is no domain to build a `site:` query from. The probe is an
open query with the merchant name as a term, which is weaker than a site-scoped
search of a vetted domain, so its results are tagged `source: 'fallback'`. Capped
at 3 merchants and gated on "no configured retailer found anything", since each
probe costs a Serper call plus a Puppeteer render plus a GPT-4o call.

**K&L is gated on evidence that already existed (WI-8).** "K&L's price can't be
verified" had been conflated with "we have no idea whether K&L stocks it". The
second was never true — `querySerper` was computing whether a relevant K&L
listing appeared and throwing it away. It now reports it, and the entry is
offered only when there is a reason to. Gating also restored reachability of
`emptyPriceData()`, which had been unreachable since something was always being
appended.

## Bugs found and fixed beyond the spec

- **`RENDERED_HTML` in the price test fixture never contained the producer.** Not
  a product bug, but it meant the new positive verification signal dropped every
  retailer in the suite. The fixture had been standing in for "a page that shows
  results" while containing nothing that identified the wine — which is precisely
  the shape of page the old negative-only check waved through.
- **A test asserted an unreachable state.** "Marks a retailer unverified when the
  wine records no producer" cannot be reached via `fetchPriceData`: a wine with no
  producer fails `isAcceptableMatch` upstream, so no retailer survives to be
  verified. Moved to a direct unit test of `pageMentionsProducer`, where the
  `null` return is real and reachable.
