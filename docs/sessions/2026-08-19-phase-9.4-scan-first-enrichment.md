# 2026-08-19 — Phase 9.4: scan-first enrichment and the draft/promote decision

**Branch:** `feature/discovery-review-ui`
**Spec:** `docs/specs/2026-08-19-phase-9.4-scan-first-enrichment.md`
**Status:** WI-1 through WI-8 complete and committed.

## What was done

`docs/CLAUDE.md`, `wine-app-product-context.md`, and the spec itself were already
updated (uncommitted) at the start of this session — the doc-writing pass had happened
separately from the build. This session built the code to match, in the spec's stated
commit order:

1. **WI-2 — Draft/promotion model.** Migration `005_phase9_4_draft_promotion.sql` adds
   `promoted_at` (nullable ISO timestamp), backfilled from `date_added` so every existing
   row stays visible. `WineFilter.include_drafts` (default false) gates whether
   `listWines` includes drafts; `getWine` always returns them. `CreateWineSchema`'s
   `tag_discovered` default flips `true` → `false`. `POST /:id/promote` sets the three
   list tags and `promoted_at` in one call, 400s when none is set, and is idempotent
   (`promoted_at` only ever set once).
2. **WI-7 — Delete and the 24h sweep.** `DELETE /api/wines/:id` (409 if the wine has a
   tasting note), `StorageAdapter.deleteWine`/`sweepStaleDrafts`, and a sweep on server
   start plus every 24h thereafter (`server.ts`).
3. **WI-3 / WI-5 — Tiered reviews and tier-aware TTL.** `fetchReviewData` accepts
   `tier: 'primary' | 'full'`; primary returns after the primary retailer pass regardless
   of outcome, recording `reviews:skipped:tier-primary:*` avoided-call labels only when
   the tier boundary actually changed the outcome (primary found nothing). The
   `fetch-reviews` route accepts `?tier=`, coalesces per-tier
   (`${id}:fetch-reviews:${tier}`) so an in-flight primary auto-fire can't be joined by a
   concurrent full-tier click, and `reachedExtendedTier` (new,
   `routes/enrichment-cache.ts`) makes the TTL cache tier-aware by reading
   `review_probe_log` rather than adding a column.
4. **WI-1 / WI-4 / WI-6 — Frontend rewiring.** `LabelScanFlow.tsx` now creates the wine
   row immediately after `scanLabel` resolves; the confirm/edit screens are PATCH forms
   over that real row (`updateWine`), not `CreateWineInput` builders. A free duplicate
   check (`web/src/utils/duplicateMatch.ts`, reusing `scoreMatch`) runs first against the
   promoted wines already in the collection — a confident match short-circuits straight to
   that wine's `DiscoveryReview`, a vintage mismatch surfaces a notice but still creates a
   new draft. Once created, `fetchWinePrice`/`fetchWineReviews({tier:'primary'})` fire
   fire-and-forget if Tier 1 parsed; held until Continue otherwise, and re-fired
   (`force: true`) if an identity field was edited before Continue.
   `DiscoveryReview.tsx` now renders two modes off `wine.promoted_at`: draft (three-way
   tag select, Save to Collection disabled until one is picked, Discard) and promoted
   (unchanged pre-9.4 behaviour — this is how a duplicate-matched existing wine is shown).
   A new `autoFireReviews` prop mirrors the existing price mount-effect for reviews, so
   the screen joins whatever `LabelScanFlow` already started via the same
   coalescing/TTL path rather than a second one.
5. **WI-8 — Docs.** `docs/build-phases.md` Phase 9.4 entry added (product-context.md and
   CLAUDE.md were already current, see above). This file.

## Key decisions and rationale

- **`createWine` now always sets `promoted_at: null`, unconditionally** — even when a
  caller (e.g. `backend/db/seed.ts`) explicitly supplies `tag_discovered: true`. Tags and
  draft state are orthogonal now; promotion is the only thing that sets `promoted_at`.
  `seed.ts` was updated to promote each wine immediately after creating it, since it's
  meant to simulate an already-populated collection.
- **`reachedExtendedTier`'s one accepted false negative**, documented in its own comment:
  a `tier=full` run that itself succeeded within the primary tier never touches the
  extended tier either (existing `foundNoScore` gate), so its probe log is
  indistinguishable from a primary-only auto-fire's. The heuristic over-invalidates that
  case — one extra bounded primary-tier re-run, not a wrong result — rather than adding a
  column, matching the spec's explicit tradeoff.
- **True request cancellation on identity edit was not built.** The spec's WI-6 step 5
  says "abort the in-flight run and re-fire"; the existing `coalesce()` primitive is keyed
  only by `id:tier`, with no way to signal "start a new run regardless of one in flight."
  Re-firing with `force: true` on an identity edit guarantees a fresh, correct search
  gets queued and is the one whose result the UI ultimately shows, but if the pre-edit
  auto-fire is still genuinely in flight at that moment, both requests can only run
  sequentially (coalesce joins them) rather than the second one truly cancelling the
  first. In practice this only matters if the developer edits an identity field inside
  the ~1–3 second primary-tier search window, and the cost either way is bounded at one
  extra primary-tier run.
- **The scan-flow duplicate check fetches a fresh, unfiltered `listWines()` when the
  scan overlay opens**, rather than reusing `App.tsx`'s tab-filtered `wines` state. The
  spec says "the wine list already in App.tsx state," but that state is scoped to
  whichever tab is active — matching only within the current tab would miss a duplicate
  sitting in a different list. The fresh call costs nothing (a local DB read, not a
  metered call) and is the same query `listWines()` already makes elsewhere.

## Bugs found and fixed (during this session, not shipped)

- `reviews.test.ts`/`price.test.ts` fixtures and `sqlite-adapter.test.ts`'s `listWines`
  helpers predated `promoted_at`; adding the field to `WineEntry` surfaced them as
  compile errors and, for the storage-adapter list tests, as newly-correct failures
  (drafts are excluded by default now) rather than as Phase 9.4 defects. Updated fixtures
  and had the list-filter tests promote their wines, since those tests are about
  tag/region/rating filtering, not draft state — draft exclusion itself got its own
  dedicated test block.
