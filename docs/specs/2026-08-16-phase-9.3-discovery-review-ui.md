## 1. Context in one paragraph

The last several phases (7 through 9.2) improved the accuracy and cost of retailer
prices, reviews, drinking windows, and quality signals *after* a wine is already saved.
The screen the developer actually sees in the first ten seconds after a scan or a manual
add has not been touched since Phase 6.5 and has drifted out of step with what the app
now does: it asks for a `cellar_category` that nothing downstream reads, it auto-fetches
only price (never reviews — the signal the developer most wants before deciding whether
to keep a wine), it shows a label image that was never being saved in the first place,
its copy still says "Wine-Searcher" for a price source that has been Serper for several
phases, and the manual "+ Add Wine" path skips this screen entirely — a hand-entered wine
gets no price, no reviews, and no decision support at all. This phase rebuilds that one
screen, in priority order the developer stated directly: reviews first, then whether a
preferred retailer carries the wine, then a wishlist/cellar/discovered decision, then a
price sanity check — using only the enrichment mechanism Phase 9.2 already built, so the
post-scan experience is not a second, divergent implementation of "fetch reviews" and
"fetch price."

## 2. Decisions already made — do not re-litigate

- **No new Serper call sites.** This phase changes *when and how prominently* the
  existing `fetch-reviews` (click-gated, ~12–42 credits pre-WI-7 calibration) and
  `fetch-price` (~1 credit, already auto-fetched on save) actions are presented. It does
  not add a call, a query variant, or a fallback pass. See §6 for the cost arithmetic.
- **Reviews stay user-initiated.** Making reviews the top priority means making the
  "Fetch Reviews" button the first, most prominent action on the new screen — not
  firing it automatically on save. Auto-firing it would spend ~12–42 credits on every
  scan and every manual add regardless of whether the wine is kept (abandoned scans,
  duplicates, mis-scans included), which is exactly what Phase 9.2 §6 ruled out
  ("Enrichment stays user-initiated. No auto-enrichment or background refresh."). If the
  developer wants this traded off differently after living with the prominent-button
  version, that's a one-line follow-up, not part of this phase.
- **`cellar_category` is not removed from the schema.** It stops being asked for at
  creation (§4, WI-1) but the column, type, and stored values are left alone — same
  treatment CLAUDE.md already gives `expert_reviews` and `community_sentiment`: a
  reserved field, documented as such, not a migration.
- **Both creation paths (scan and manual add) end on the same screen.** Today only the
  scan flow has any post-save screen, and even that one only fetches price. This is a
  bug in product terms, not a feature gap to defer — see §4, WI-2.

## 3. Current state — what exists today, verified against the code

- `LabelScanFlow.tsx`'s `ScanResultCard` and `ScanEditForm` (the pre-save review/edit
  screens) both render a `Cellar category` `<select>` and send its value in
  `CreateWineInput`. Nothing in `WineCard.tsx`, `WineDetailModal.tsx`, or `WineList.tsx`
  ever reads `cellar_category` — it is stored and never displayed anywhere in the running
  app. `AddWineForm.tsx` collects the same field the same way.
- `LabelScanFlow.tsx`'s `EnrichingCard` (the post-save screen) fetches only price, via
  its own `useEffect` calling `fetchWinePrice` directly — not `useEnrichmentAction`, so it
  gets none of Phase 9.2's freshness/cache/force UI. It never calls `fetchWineReviews`.
  Its copy reads *"Fetching prices from Wine-Searcher…"* and, on failure, *"check your
  Wine-Searcher API key"*. Pricing has been sourced from Serper's Shopping endpoint since
  Phase 6; `docs/CLAUDE.md`'s Phase 5 schema note already documents the original
  Wine-Searcher-API design as abandoned, with vestigial `ws_*` SQL columns nothing reads
  or writes. This copy is that abandonment leaking into the live UI, never swept — this
  is almost certainly the "wine searcher query" the developer remembered seeing run.
  `WineCard.tsx` and `WineDetailModal.tsx` carry the same stale "Wine-Searcher" wording in
  comments (not user-visible, but misleading to the next person who reads them).
- `AddWineForm.tsx`'s `onSubmit` returns `Promise<void>`, and `App.tsx`'s
  `handleFormCreate` closes the form and refreshes the list immediately on save — there is
  no post-save screen at all for a manually-added wine. `handleScanSave`, by contrast,
  returns the created `WineEntry` so `LabelScanFlow` can drive its (price-only) enriching
  step. This asymmetry is the clearest single gap: identical action (create a wine),
  completely different amount of decision support.
- No tag decision is offered at creation. `tag_discovered` is set `true` automatically;
  `tag_wishlist`/`tag_cellar` only become choosable later, from `WineCard` or
  `WineDetailModal`'s tag-toggle row (`PATCH /api/wines/:id` via `updateWine`).
- The label image shown on both `ScanResultCard` and `EnrichingCard` is a same-session
  `URL.createObjectURL(file)` preview only. `label_image_url` is hardcoded `null` in every
  `CreateWineInput` built by both `LabelScanFlow` and `AddWineForm` — the photo was never
  going to persist past the browser tab. Removing the on-screen image costs nothing that
  wasn't already being thrown away.
- "Preferred retailer" already exists as data: every entry in `PriceData.retailers` (from
  the existing, already-auto-fetched price call) carries `is_preferred_retailer: boolean`
  — `true` for any of the 12 retailers in `RETAILER_CONFIG`, `false` for an open-web
  fallback result. Nothing currently summarizes this as a single "does anyone I trust
  carry this" answer; it's only visible by reading the full per-retailer list.
- There is no delete/discard endpoint. `backend/routes/wines.ts` exposes `POST`, `GET`,
  and `PATCH` only. A wine the developer decides not to keep currently just sits
  `tag_discovered = true` with nothing else set — there is no way to remove it from this
  screen or any other. Out of scope here (§6); noted for a future phase if wanted.

## 4. Work items

### WI-1 — Stop collecting `cellar_category` at creation

- Remove the `Cellar category` `<select>` from `ScanResultCard`, `ScanEditForm`
  (`LabelScanFlow.tsx`), and `AddWineForm.tsx`.
- All three `CreateWineInput` payloads send `cellar_category: null` unconditionally
  (drop the `cellarCategory` state entirely rather than defaulting it silently).
- No backend or schema change. `cellar_category` remains on `WineEntry`/`schema.sql`,
  documented as reserved (WI-7).

**Acceptance:** neither creation path shows or writes a user-chosen `cellar_category`.
Existing stored values are untouched (the field was already unread everywhere else).

### WI-2 — Unify the two creation paths behind one post-save screen

- Change `AddWineForm`'s `onSubmit` prop from `(data: CreateWineInput) => Promise<void>`
  to `(data: CreateWineInput) => Promise<WineEntry>`, mirroring `LabelScanFlow`'s existing
  `onSave`.
- `App.tsx`: both `handleFormCreate` and `handleScanSave` resolve to the same new state
  (e.g. `reviewingWine: WineEntry | null`) that mounts the screen built in WI-3, instead of
  `handleFormCreate` closing immediately.

**Acceptance:** a wine created via `+ Add Wine` reaches the identical post-save screen a
scanned wine does. No behavior change to the pre-save `AddWineForm` fields themselves.

### WI-3 — Discovery Review screen, built from existing enrichment plumbing

New component (e.g. `web/src/components/DiscoveryReview.tsx`) replacing
`LabelScanFlow`'s `EnrichingCard`, rendered by `App.tsx` for both paths from WI-2.

Reuses, unchanged: `useEnrichmentAction`, `fetchWineReviews`/`fetchWinePrice`,
`EnrichmentFreshness`, `PriceSection`, `CriticScoreBadges`, `updateWine`. No new route,
no new fetch path, no parallel cache — the bar CLAUDE.md §5 already applies to backend
modules ("would a fix here need to be manually re-applied elsewhere?") applies here too:
`EnrichingCard`'s bespoke price-only `useEffect` is exactly that kind of duplication, and
this WI removes it rather than extending it.

Section order, top to bottom, in the developer's stated priority:

1. **Identity header** — producer / denomination / vintage / region. No image (WI-5).
2. **Reviews** — `Fetch Reviews` button, same label/behavior as `WineCard`'s (click-gated,
   `wine.review_data ? 'Refresh Reviews' : 'Fetch Reviews'`). `CriticScoreBadges` renders
   results as they arrive. This is the first action the screen presents — not run
   automatically (see §2).
3. **Preferred retailer carry-check** — one-line summary from WI-4, appears once price
   data exists.
4. **Price** — `PriceSection`, unchanged. Price keeps its existing auto-fetch-on-mount
   behavior (pre-existing since Phase 6, ~1 credit — not new spend introduced here).
5. **List decision** — `tag_wishlist` / `tag_cellar` toggle buttons, same `updateWine`
   PATCH pattern as `WineCard`'s tag row. `tag_discovered` is shown as already set
   (creation default) and is not offered as a choice here — removing it entirely is still
   available from the wine's card/detail view, unchanged.
6. **Done** — closes the screen, same as today.

**Acceptance:** `Fetch Reviews`/`Fetch Price` on this screen produce identical
`cached`/`fetched_at`/`force` behavior to the same actions on `WineCard`, because they
call the same hook against the same endpoints.

### WI-4 — Preferred-retailer carry-check (frontend-only, no new Serper cost)

- New pure function, e.g. `web/src/utils/preferredRetailers.ts`:
  ```ts
  export function summarizePreferredRetailers(priceData: PriceData | null): {
    carried: RetailerPrice[]
    totalConfigured: number
  }
  ```
  filters `priceData.retailers` on `is_preferred_retailer`; `totalConfigured` is the
  length of `RETAILER_CONFIG` (imported from `shared/config/retailers.config.ts`, already
  shared-safe per CLAUDE.md §5).
- Rendered as one line: *"Carried by K&L, Flatiron — 2 of 12 preferred retailers"* or
  *"Not yet seen at a preferred retailer"* when `carried.length === 0`.
- Entirely computed from data the existing price fetch already returns. Zero new
  requests, zero new backend surface.

**Acceptance:** the summary updates the instant `price_data` populates; no additional
network call attributable to it in `GET /api/debug/serper-usage`.

### WI-5 — Remove the label image from both review screens

- Drop the `scan-result-image-wrap`/`<img>` block from `ScanResultCard`, `ScanEditForm`,
  and the new `DiscoveryReview` screen.
- Before removing, re-confirm `label_image_url` is still hardcoded `null` in both
  `CreateWineInput` builders (§3) — don't delete the only display of a field that some
  other change in flight has started persisting.

**Acceptance:** neither screen renders an image. Reclaimed space goes to WI-3's sections,
not left blank.

### WI-6 — Retire stale "Wine-Searcher" copy

- `LabelScanFlow.tsx`: replace *"Fetching prices from Wine-Searcher…"* and *"check your
  Wine-Searcher API key"* with the same "Retailer Crawl" framing `PriceSection.tsx`
  already uses correctly. (Moot in `EnrichingCard`'s case since WI-3 removes that
  component outright — apply this inside the new `DiscoveryReview` screen instead.)
- `WineCard.tsx` comment *"Price data from Wine-Searcher"* and `WineDetailModal.tsx`
  docblock *"Wine-Searcher price section"* — update to name Serper/Retailer Crawl.

**Acceptance:** no string or comment containing "Wine-Searcher" remains in
`LabelScanFlow.tsx`, `WineCard.tsx`, or `WineDetailModal.tsx`.

### WI-7 — Documentation (no code)

- `docs/CLAUDE.md` §3: add a "### Phase 9.3 — Discovery review UI" paragraph in the same

## 6. Out of scope — do not do these

- Any new Serper call site, query variant, or fallback pass. This phase is a pure
  rearrangement of when existing enrichment actions are surfaced. Net new Serper calls
  introduced: **zero**.
- Auto-firing `fetch-reviews` on save. Rejected per §2 — contradicts Phase 9.2's fixed
  decision and would spend ~12–42 credits on every scan/add regardless of outcome.
- A delete/discard endpoint or UI for a wine the developer decides not to keep. Doesn't
  exist today (§3); worth its own small phase (a `DELETE` route plus a confirmation
  control) if wanted, not bundled here.
- Any change to review tiering, TTLs, the probe log, or fallback-URL resolution — Phase
  9.2 owns those and none of them are reopened by this phase.
- iOS. Web only, matching the current phase's scope.
- Changing `tag_discovered`'s auto-set-on-creation behavior.

## 7. Definition of done

- A wine created via **Scan Label** or **+ Add Wine** lands on the same Discovery Review
  screen (WI-2, WI-3).
- Neither creation path shows or writes `cellar_category` (WI-1).
- Neither creation-flow screen renders the label image (WI-5).
- `Fetch Reviews` is the first enrichment action presented on the new screen, remains
  click-gated, and uses the same hook/endpoint/TTL/force semantics as `WineCard`'s (WI-3).
- A one-line preferred-retailer summary renders once price data exists, backed by zero
  additional Serper calls (WI-4).
- `tag_wishlist`/`tag_cellar` are toggleable from the new screen via the existing
  `updateWine` PATCH (WI-3).
- No string or comment containing "Wine-Searcher" remains in `LabelScanFlow.tsx`,
  `WineCard.tsx`, or `WineDetailModal.tsx` (WI-6).
- `docs/CLAUDE.md` and `docs/wine-app-product-context.md` updated per WI-7.
- Existing backend/web suites still green; new tests added for `DiscoveryReview` and
  `summarizePreferredRetailers`. `tsc --noEmit` clean in both projects.
