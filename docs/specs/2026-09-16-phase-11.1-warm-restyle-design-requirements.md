# Phase 11.1 — Warm restyle from a second Claude Design canvas (states, edge cases & scale)

**Status:** Design complete, developer-approved after two review rounds (2026-09-16).
Not yet applied to `web/src` — this document is the spec for that implementation work.

**Why this exists:** Phase 11 (2026-09-04) verified the running app against the
*original* 2026-08-25 canvas's visual system, hand-extracted into `web/src/index.css`
(`--bg:#121212`, `--blue:#1D6AE5`, `--yellow:#FFC729`, Newsreader + Manrope). The
developer ran a second, independent design pass in Claude Design
(`https://claude.ai/code/artifact/d73f172b-578c-4757-b44d-5c8e43a840c2`) specifically to
see whether a different Anthropic product would converge on a meaningfully different UI
from the same starting material, liked the result, and asked for it applied in place of
the current Phase 11 visual system. This document is that decision, recorded the way
every prior phase in this file has recorded one.

**Decision recorded 2026-09-16 — toolchain exception (`CLAUDE.md` §12):** Claude Design
is a distinct Anthropic product from the Design skill + Claude.ai Artifact workflow this
project has used through Phase 11. Introducing it required — and got — an explicit
developer decision, per §12's standing rule. Two canvases were run for comparison: one
blind to this repo (fed only a portable brief's Sections 1–5 — vision, hotspots, data
model, shipped screen inventory, cross-cutting principles — deliberately withheld the
Phase 10/11 palette and the codebase itself), one that read `web/src` directly. The
developer reviewed both and chose to continue with the blind pass, then had it corrected
against the real component set and extended to cover states neither original canvas did.
See `CLAUDE.md` §12 for the toolchain note this phase adds.

**Decision recorded 2026-09-16 — reverses `docs/specs/2026-09-01-phase-10-v2-web-ui-design-requirements.md`
§2:** that document required the four real tabs to render "inside the tab-bar shell...
not a sidebar-nav page," specifically correcting the original 2026-08-25 canvas's
six-hotspot sidebar back to a top tab bar. This phase reintroduces a sidebar — not the
six-hotspot one that decision was written against, but the same four real tabs
(Discovered, Wishlist, Cellar, Tasting Notes), flat, in a left nav instead of a top bar.
Recorded here as a deliberate developer choice made during this session's canvas review,
not an oversight of the earlier decision — a future session should not "fix" this back
to a tab bar without checking here first.

## 2. Canvas contents (as of 2026-09-16)

Seven screen artboards, built against the real `shared/types.ts` schema and the real
components read from this repo (`App.tsx`, `WineCard.tsx`, `CellarStats.tsx`,
`DiscoveryReview.tsx`, `WineDetailModal.tsx`, `EvaluateForm.tsx`, `PriceSection.tsx`,
`CriticScoreBadges.tsx`, `AttributedDrinkingWindows.tsx`):

- `Main.dc.html` — Cellar tab (landing), with `CellarStats`-equivalent capacity tile and
  region/color allocation bars.
- `Discovered.dc.html` — the quick add/remove tag row, not the full four-way toggle.
- `Wishlist.dc.html`, `TastingNotes.dc.html` (with the rating filter).
- `DiscoveryReview.dc.html` — draft mode: unsaved badge, price still loading (the real
  auto-fetch-on-mount state), Discovered pre-checked.
- `WineDetailModal.dc.html` — full pricing table including the real verification /
  vintage-mismatch / non-standard-format / link-only retailer badges.
- `Evaluate.dc.html` — real WSET fields, tannin correctly omitted for a white wine, and
  the post-save tag-review step.

Four reference-sheet artboards added 2026-09-16, covering states neither the original
2026-08-25 canvas nor this canvas's first pass designed for:

- `EmptyStates.dc.html` — all four tabs empty. Carries the real copy verbatim
  (`WineList.tsx`: `"No wines here yet."`) and the real conditional behavior
  (`CellarStats` renders nothing at all, not an empty tile, when `wines.length === 0`).
  The supporting sentence under each headline is a proposed addition, flagged as such on
  the board — the shipped app has no such copy today.
- `ErrorStates.dc.html` — list-load failure, enrichment fetch failure, `EvaluateForm`
  required-field validation, `AddWineForm` save failure, retailer-link save failure, and
  the three `LabelScanFlow` non-happy-path steps (Unavailable / Failed / Already in Your
  Collection). All copy is verbatim from `App.tsx`, `AddWineForm.tsx`, `EvaluateForm.tsx`,
  `LabelScanFlow.tsx`, and `RetailerLinksSection.tsx`.
- `EdgeCases.dc.html` — NV vintage, all four list tags active on one wine simultaneously,
  a disputed drinking window across five critics, an unnormalized (`known_publication:
  false`) critic source, zero price matches, cellar capacity over 100%, and a long
  producer/denomination wrap test.
- `DenseData.dc.html` — an 11-region allocation table, a proposed compact list row for
  scale (see Notes), and one wine card with every optional field in `WineEntry` populated
  at once.

## 3. What to preserve exactly

This is a re-skin, not a re-architecture. Nothing below should change:

- Tier 1 fields always shown; Tier 2 fields (classification, vineyard, cuvée, grape
  varieties, color) collapse entirely when null — no empty rows, no dashes.
- List tags are additive booleans, never a lifecycle.
- The `Sourced` marker distinguishing a derived (`drinking_window_source` /
  `vintage_rating_source === 'derived'`) value from a manually-entered one.
- Each critic score its own badge, its own voice — never blended, never prioritized (see
  Phase 11's own note on this — still settled, not open).
- The scan-path draft/promote flow: a draft is saved and enriched immediately but
  invisible in every list until a list tag is chosen and it's explicitly promoted.
- Metered enrichment (price, reviews) stays user-initiated, click-gated, except the one
  narrow scan-path auto-fetch exception already in `LabelScanFlow`/`DiscoveryReview`.

## 4. Open before implementation

- The canvas's wine data is illustrative placeholder content (invented but plausible
  producers/vintages), not `wine.db` rows — unlike the Phase 10/10.5 canvases, which
  pulled real collection data on purpose specifically to surface real gaps. Re-verify
  layout against real rows before treating the mockup's field combinations as exhaustive.
- `TastingNoteHistory` and the two creation-entry modals' own internal steps
  (`LabelScanFlow`'s upload/scanning steps, `AddWineForm`'s field list) don't have
  artboards yet — needed before this phase's re-skin is complete, not just the six
  screens above.
- The dense-data board's compact list row (a slimmer row style proposed for tabs past
  roughly 15 wines) does not exist in the shipped app today and needs a developer
  decision, not just a visual once-over, before it's built.
