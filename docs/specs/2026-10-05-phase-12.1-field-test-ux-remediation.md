# Phase 12.1 — Field-test UX remediation (web + iOS)

> Wine app project | Written 2026-10-05 in Claude AI (Cowork) from the developer's 2026-10-04 device test | Status: **spec, not started**
> Read alongside `docs/CLAUDE.md` (rules) and `docs/build-phases.md` (Phase 12 build log). Companion: `2026-10-05-phase-12.2-enrichment-accuracy-and-transparency.md`.

## 1. Goal

The developer uploaded the real cellar through the iOS app and wrote down what felt wrong. This phase fixes the **interface and data-flow** half of that list on **both** frontends. The **enrichment-accuracy** half (wrong bottling, missing retailers, price not shown, and so on) is Phase 12.2 and is built second.

The feedback came from the iOS app, but most of it is not iOS-specific. Where the web has the same behaviour, it is fixed there too, in the same phase. Every work item below says what changes on each surface. Section 5 is a per-surface checklist.

## 3. What the code already does (verified 2026-10-05 against `main` @ `2fa7c5c`)

Recorded so Claude Code does not re-derive it, and so the work items below are scoped against reality rather than the screenshots alone.

- **Draft review (iOS, `DraftReviewView.swift`)** — the "Review" screen after a scan. Critic scores render only when found; **if nothing is found the block disappears** (an explicit choice in implementation spec §6.4: "never an empty state mid-task"). That is exactly the "I can't tell whether nothing was found or it's still loading" complaint. The Price block shows min / avg / max and one "Nearest:" line (not tappable, not underlined) — no retailer list at all.
- **Save to collection** — the list picker rows (`Discovered`, `Wishlist`, `Cellar`) show a checkmark only when **on**, so an unselected row is indistinguishable from plain text. The button is `.disabled` plus `opacity 0.4`, and the hint "Pick a list first." sits **below** the button.
- **Colour** — a SwiftUI `Picker` in `WineFieldsSection` ("Unknown / Red / White / Rosé"). The "white" the developer saw on the post-scan snapshot has not been reproduced; see WI-8.
- **Drinking window on the iOS list row** reads only the wine-level `drinking_window` (`WineRowView.swift`). On a wine whose critics disagree it is `nil`, so the row shows nothing even though the detail view (`WineDetailView.swift`) shows attributed per-critic windows. `DrinkReadiness.of(...)` also reads only the wine-level window, so those wines count as **No window**. Both of the developer's drinking-window complaints share this cause.
- **Delete** exists on iOS (long-press → Delete, confirmed) and on the backend (`DELETE /api/wines/:id`), but the route **returns 409 when the wine has any tasting note**. There is no Edit screen: identity fields are editable only during draft review.
- **`price_paid`** is on the wine model (`Wine.swift`, `shared/types.ts`) and is written as `null` by every creation path. It is never shown or edited.
- **"Reviews" label collision** — the iOS detail screen has a metered **Reviews** action (critic scores) and a **Reviews** disclosure card (`WineDetailView.swift:352`) that actually holds the developer's own tasting notes ("No notes", "N notes").
- **Verified / Unverified** badges render with no explanation (`DetailFormatting.swift`). Authoritative definitions are in `shared/types.ts` (`VerificationState`): *verified* = the shop's live search page rendered and its visible text contains every significant word of the producer; *unverified* = the check could not complete (render failed or timed out, or the wine has no producer recorded); *unchecked* (no badge) = never attempted (K&L's link-only entry, and product pages the reviews module already rendered). **None of the three says anything about vintage or bottling.**
- **Carry-over bug** — PR #42 fixed lists not reloading when a scan's lookups landed, and the detail screen not re-reading the wine. The developer still reported reviews appearing after save but not in the preview. Treat as **not closed** until WI-9's parity check passes.

### WI-1 — Edit a saved wine (web + iOS)

There is no Edit screen after a wine is saved. Add one, reusing the draft form's field components (`WineFieldsSection` on iOS, the shared form on web).

**Fields:** producer, denomination, vintage (blank = NV), region, classification, vineyard, cuvée, colour, **price paid**, **drinking window** (start/end, optional), plus the existing list tags and bottle quantity. **Delete wine** is a destructive button at the bottom (WI-3).

**Price paid** — the existing `price_paid` field, labelled "Price paid", optional, never required to save, shown on the detail view when set. *(Assumption — see §8 Q1: the developer wrote "price" without saying paid vs. seen.)*

**Drinking window** — optional. Setting it writes `drinking_window_start/end` with `drinking_window_source = 'manual'`, which Phase 8 already protects from automated overwrite. This is the **primary window** (D2). Clearing it removes the manual value and returns the wine to the derived/critic state. If the wine has a derived window and the developer has not set one, the field is **pre-filled from the derived value** and labelled "from critics". The pre-fill is display only: saving without touching it does **not** convert it to a manual value (that would silently stop future automatic updates).

**Identity change → "Refresh searches now?" (D4).** On save, if any identity field (`producer`, `denomination`, `vintage`, `vineyard`, `cuvee`, `quality_classification`) differs from the stored value **and** the wine has `price_data` or `review_data`:
- **Yes** → run price + reviews with `force=true`. The prompt states the credit estimate (WI-7's constants).
- **No** → keep the old data, and mark it stale: record the identity the data was fetched for **inside the JSON blobs** (`price_data.enriched_for`, `review_data[].enriched_for`, the string `identityOf(wine)` returns — no migration). When it differs from the current identity, both the price and review sections show **"Fetched for a different version of this wine — may not match. Refresh."** A blob without `enriched_for` (everything stored before this phase) is treated as unknown: **no flag**, per the "stored enrichment JSON is older than its types" rule in Phase 12's build log.
- A change to colour, price paid, window, tags or quantity never prompts.

**Acceptance:** edit producer on a wine with data → prompt appears; Yes spends credits once and replaces the data; No leaves the data with the stale notice; editing quantity alone never prompts.

### WI-2 — Primary vs. informational drinking windows; "Check window"; fourth Ready segment

**Definitions (single backend definition — do not port to Swift):** add a derived field on every wine read, in the same way `latest_tasting_note_date` was added in Phase 12 (computed in the read path, not stored, no migration):

`window_status: 'primary' | 'check' | 'none'`
- `primary` — the wine has a wine-level `drinking_window` (manual, or derived from agreeing critics).
- `check` — no wine-level window, and `review_data` carries **two or more** critic windows that disagree (the situation `derive-wine-level.ts` resolves to `null` today).
- `none` — no wine-level window and no critic window at all.

A single critic's window is, by the existing rule, a derived primary window — it never produces `check`.

**List views (web + iOS):** a `primary` wine shows its window as today. A `check` wine shows a **"Check window"** flag where the window would be. A `none` wine shows nothing. The flag is a list-view element only (D3).

**Ready-to-drink widget:** four segments — **Ready now · Needs more time · Check window · No window**. Counts stay *wines, not bottles*. `Past window` still counts under Ready now (Phase 12 decision). Only a `primary` window can place a wine in Ready now or Needs more time; a `check` wine is **never** guessed at from the per-critic windows. Tapping **Check window** filters the cellar list to those wines.

**Detail view (web + iOS):** two visually distinct groups:
1. **Your window** (when set) or **Window (from critics)** with the Sourced marker (when derived) — the primary window, in the normal text style.
2. **Critic windows (for reference)** — one row per critic with attribution, in a muted style with a "reference only" label. Shown whenever any exist, whether or not a primary window is set, so a manual window never hides what critics said.

**Rules carried forward:** per-critic windows are never blended or averaged (`CLAUDE.md` §15); a manual window is never overwritten by an automated run (Phase 8). The developer may *choose* to blend or to adopt one critic's window — by typing it into Edit — which is a manual value, not a system blend.

**Acceptance:** a wine with two disagreeing critic windows and no manual window shows "Check window" in the list, per-critic rows on detail, and counts under **Check window**; entering a window in Edit moves it to Ready now / Needs more time on next load, the flag disappears, and the critic rows remain as reference.

### WI-3 — Delete a wine; tasting notes outlive it (migration 008)

**Schema (migration `008_phase12_1_notes_independent.sql`):** SQLite cannot drop `NOT NULL` in place, so rebuild `tasting_notes`:
1. Create `tasting_notes_new` with `wine_id TEXT REFERENCES wines(id) ON DELETE SET NULL` (nullable) and five snapshot columns: `wine_producer TEXT`, `wine_denomination TEXT`, `wine_vintage INTEGER`, `wine_vineyard TEXT`, `wine_cuvee TEXT`.
2. Copy every row, backfilling the snapshot from the current `wines` row.
3. Drop the old table, rename the new one, recreate any index.
4. Written to be safe under the `schema_migrations` runner (each file runs once; PR #45) and verified on a **copy of the real database** before merging, as PR #45 was.

New notes written after this phase copy the snapshot at save time. `wines.latest_tasting_note_id` is unchanged.

**API:**
- `DELETE /api/wines/:id` no longer returns 409. With `?dry_run=1` (or a count in a pre-flight GET) the client learns how many notes will be kept so the confirmation can name them. The wine row is deleted; its notes stay with `wine_id = NULL`.
- The Notes tab/list must read from `tasting_notes` directly rather than through `wines.latest_tasting_note_id`, so a detached note still lists. Claude Code to check whether a notes-list route exists; if not, add `GET /api/tasting-notes`.
- `ON DELETE SET NULL` needs `PRAGMA foreign_keys = ON`; confirm the adapter sets it, and add a test that fails if it does not.

**UI (web + iOS):**
- Delete confirmation names the consequence: *"Delete this wine? Its 2 tasting notes stay in Notes, marked 'wine removed'."* Wines with no notes keep the existing short confirmation.
- A detached note shows its snapshot identity plus a **"Wine removed"** tag, and opens read-only (no Evaluate, no price/review actions).
- Delete is reachable from the Edit screen (WI-1) as well as the existing long-press, so it is discoverable.
- "Remove from lists" (untag) stays exactly as it is and is **not** conflated with Delete.

**Acceptance:** delete a wine that has a note → wine gone from every list, note still listed under Notes with its original producer/denomination/vintage and "Wine removed"; evaluating that wine later (if re-added) starts a fresh note history.

**Rule change to record:** `CLAUDE.md` §3 says `tasting_notes.wine_id` is "UUID, not null". Update at the original claim when this ships (see §9).

### WI-4 — Preview screen: contents, loading, empty and failed states (web + iOS)

Rebuild the post-scan review's **critic** and **price** blocks (`DraftReviewView.swift`'s `CriticScoresBlock` / `PriceBlock`; `DiscoveryReview.tsx` on web). Section order stays: identity fields → **Critic reviews** → **Price & retailers** → list picker → Save/Discard.

**Critic reviews block** — four explicit states, never a vanishing block:

| State | Shows |
|---|---|
| Looking | Two skeleton lines + "Looking for critic scores…" |
| Found | Score, publication, **vintage the score applies to**, and the critic's window if stated (D10). A score whose vintage ≠ the wine's is muted and tagged with its year (see §8 Q2 for the list-badge rule). |
| Nothing found | "**No critic scores found yet** for this wine." + the existing "Search more retailers" action (extended tier, still click-gated). Replaces the disappearing block. This is also the answer to the scratched "evaluate from a photo" idea: the card is always present and honest about what it has. |
| Failed | "Review lookup failed — Try again" |

**Price & retailers block** (D7) — one block, grouped with its retailers:
- **Avg · High · Low** (labels spelled out; today's "Min/Avg/Max" line).
- **Nearest retailer** — name, price, **tappable and underlined** (D9). Opens the retailer's product page (resolving on tap exactly as the detail view does).
- **"N more retailers"** — collapsed by default; expands to the retailer rows with the same badges as the detail view (WI-8's explanations apply).
- **When no average can be computed but listings exist** — never a row of dashes. State why, in plain language, with counts: *"5 listings found, none counted toward the average: 2 other vintages (2020, 2021), 1 six-pack, 1 magnum, 1 search-only."* This is the "Marcoux" case. The exclusion breakdown is produced by the backend (Phase 12.2 WI-1 adds it to `price_data`); until then, 12.1 derives the reasons client-side from the flags already on each retailer row (`vintage_mismatch`, `pack_quantity`, `non_standard_format`, `link_only`). The existing `other_vintage_price_range` is shown as "Other vintages: $68–$199".
- **When the price lookup returned no listings at all** — "No matching listings found at the configured retailers." (exists; keep).
- States: Looking (skeleton), Found, Nothing found, Failed — same four.

### WI-5 — Scan → preview transition (web + iOS)

Today: parse → draft created → preview, with the auto-fired primary-tier lookup still running underneath. New (D8):

1. Parse returns and the draft is created → show a full-screen interstitial: **"Scan successful"**, the parsed `producer · denomination · vintage`, and *"Pulling details…"*.
2. Move to the preview **as soon as the first critic score lands**, or **after `PREVIEW_HOLD_MS = 3000`** (measured from the parse's return), whichever comes first.
3. The preview then shows WI-4's *Looking* states for anything still pending. The lookups continue; nothing is cancelled when the hold ends.

Notes: the duplicate-check prompt ("Same wine?") still takes precedence and is unaffected; a failed scan shows the existing error; the hold never delays an error. The lookups still take about a minute for a new wine (Phase 12 build log) — this changes what the developer sees while they run, not how long they take. Put `PREVIEW_HOLD_MS` in one constants file per surface so it can be tuned without a code search.

### WI-7 — Price & retailers grouping; Hard refresh (web + iOS)

**Grouping.** On the detail views today the pricing rows sit visually under the critic-scores area and read as its child. Restructure into two peer sections:
- **Critic reviews** — scores, windows (informational), its own freshness line and refresh actions.
- **Price & retailers** — avg/high/low, nearest, retailer table, **one** freshness line. The section title and the button both say *"Price & retailers"* so it is clear that refreshing price also refreshes the retailer links (as it already does; the labels just never said so).

**Buttons (D6).** In each section's action row: the normal **Refresh** button (unchanged behaviour: TTL-guarded, returns the cached result when fresh) and a separate, bordered **Hard refresh** button that sends `force=true`.
- Hard refresh replaces the "Refresh anyway" text link everywhere it exists (`DetailComponents.swift:105` and the web `EnrichmentFreshness`).
- Shown on **both** sections at all times once data exists (not only when the cache is fresh).
- Each shows its **credit estimate** under or on the button (*"Hard refresh · about N credits"*). Take the numbers from the measured Phase 9.2 figures (`docs/specs/2026-08-12-phase-9.2-enrichment-cost-reduction.md` §3) and keep them in one constants file; do not invent new ones.
- The existing two-tap confirmation on iOS is kept for Hard refresh (it spends money).
- Hard refresh on Reviews still clears the negative-probe memory exactly as "Refresh anyway" does today.
- The normal metered action label ("Fetch Reviews" / "Refresh Reviews") is **not** renamed beyond adding the section title "Critic reviews" above it, to avoid colliding with "My Review" (D11).

### WI-8 — Labels, explanations, links, colour

- **"My Review" (D11).** iOS: the `DisclosureCard(title: "Reviews", …)` at `WineDetailView.swift:352` → **"My Review"**; its summary line keeps the note count. Web: the equivalent tasting-note section in `WineDetailModal` / `TastingNoteHistory`. Nothing else is renamed "My Review".
- **Verified / Unverified explained.** Each badge is tappable (an info affordance, and underlined per D9) and opens a one-line explanation, with the long form in the retailer table's legend:
  - *Verified* — "We opened this shop's own search page and it mentions this producer." Honest scope: it does **not** confirm the vintage or the exact bottling; those have their own badges.
  - *Unverified* — "We couldn't confirm this listing (the shop's page didn't load in time, or no producer is recorded). The price is from Google Shopping and may be out of date."
  - *Search only* — "A link to the shop's search page; no price was found."
  - Unchecked shows no badge, as today.
  The wording must come from the `VerificationState` definition in `shared/types.ts`; if that definition changes, the copy changes with it.
- **Hyperlink affordance (D9).** One shared style token per surface (`.link` on web, a `LinkText` style on iOS): underlined, accent colour. Apply it to the nearest-retailer line, every retailer row link, every critic-source link, the "View" / "Use this page" actions, and the new info affordances. Add a test or lint step that fails if a tappable `Text` in a list of known link components lacks the style, so it does not regress.
- **Colour text.** Reproduce first: scan a **red** wine and a **rosé**, change the Colour picker, and confirm the displayed value follows the selection on the review screen **and** afterwards on the card/detail. The developer saw "white" on the post-scan snapshot. Candidates to rule out in order: (a) the Picker's displayed label not following its binding inside a `Form`; (b) the scan result's `wine_color` overriding the user's selection on a later PATCH/refresh; (c) a fixed string. The acceptance test is behavioural: selection → display, on every screen that shows colour.

### WI-9 — Preview/saved parity (the carry-over bug)

The developer reports that retailer links, ratings and reviewer links fetched in the preview "don't carry over" after saving, and that reviews often appear only after saving and reopening. PR #42 fixed two real causes (lists not reloading on landing; the detail screen opening from a stale copy). This item closes the loop:

1. **Reproduce first** with an instrumented run: scan a wine not in the collection, note when price and reviews land (log timestamps), save at three points (before either lands, between, after both), then open the wine from each list. Record, per point, what the preview, the list row and the detail view show.
2. **Converge the paths.** iOS enrichment currently runs through `ScanFlowModel.fireEnrichment`/`firePrice` for drafts and `WineDetailModel` for saved wines — two mechanisms. `CLAUDE.md` §5 already says the web has exactly one (`useEnrichmentAction`). 3. **Add a parity test:** a fixture wine whose price and reviews arrive after the Save tap must show identical data in preview, list and detail after one reload.

## 6. Rules carried forward — do not re-litigate

- **Metered enrichment stays user-initiated**, with the existing single exception (scan path, primary tier, once per wine, after the free duplicate check) and the Phase 12 price fetch-once rule. Nothing here adds an automatic call. The Edit prompt (WI-1) and Hard refresh (WI-7) are explicit developer actions that state their cost first.
- **Critic scores and windows are never blended.** The developer may enter a window by hand; the system may not.
- A manual drinking window is never overwritten by an automated run.
- Additive boolean tags; `promoted_at IS NULL` means draft.
- Tier 2 nulls collapse — no empty rows, no dashes. (WI-4's "why no average" sentence replaces a *row of dashes*; it is not a placeholder.)
- Stored `price_data` / `review_data` may predate any field this phase adds. New code reads every new field defensively.
- Each migration file runs once (PR #45). Migration 008 must be checked against a copy of the real database.
