## 1. Goal

The developer uploaded the real cellar through the iOS app and wrote down what felt wrong. This phase fixes the **interface and data-flow** half of that list on **both** frontends. The **enrichment-accuracy** half (wrong bottling, missing retailers, price not shown, and so on) is Phase 12.2 and is built second.

The feedback came from the iOS app, but most of it is not iOS-specific. Where the web has the same behaviour, it is fixed there too, in the same phase. Every work item below says what changes on each surface. Section 5 is a per-surface checklist.

## 3. What the code already does (verified 2026-10-05 against `main` @ `2fa7c5c`)

Recorded so Claude Code does not re-derive it, and so the work items below are scoped against reality rather than the screenshots alone.

- **Draft review (iOS, `DraftReviewView.swift`)** — the "Review" screen after a scan. Critic scores render only when found; **if nothing is found the block disappears** (an explicit choice in implementation spec §6.4: "never an empty state mid-task"). That is exactly the "I can't tell whether nothing was found or it's still loading" complaint. The Price block shows min / avg / max and one "Nearest:" line (not tappable, not underlined) — no retailer list at all.
- **Save to collection** — the list picker rows (`Discovered`, `Wishlist`, `Cellar`) show a checkmark only when **on**, so an unselected row is indistinguishable from plain text. The button is `.disabled` plus `opacity 0.4`, and the hint "Pick a list first." sits **below** the button.
- **Colour** — a SwiftUI `Picker` in `WineFieldsSection` ("Unknown / Red / White / Rosé"). The "white" the developer saw on the post-scan snapshot has not been reproduced; see WI-8.
- **Drinking window on the iOS list row** reads only the wine-level `drinking_window` (`WineRowView.swift`). On a wine whose critics disagree it is `nil`, so the row shows nothing even though the detail view (`WineDetailView.swift`) shows attributed per-critic windows. `DrinkReadiness.of(...)` also reads only the wine-level window, so those wines count as **No window**. Both of the developer's drinking-window complaints share this cause.
- **Delete** exists on iOS (long-press → Delete, confirmed) and on the backend (`DELETE /api/wines/:id`), but the route **returns 409 when the wine has any tasting note**. There is no Edit screen: identity fields are editable only during draft review.
- **`price_paid`** is on the wine model (`Wine.swift`, `shared/types.ts`) and is written as `null` by every creation path. It is never shown or edited. *(2026-10-05: the developer's "price" note meant a **manual price**, not this field — D12. `price_paid` stays unsurfaced.)*
- **"Reviews" label collision** — the iOS detail screen has a metered **Reviews** action (critic scores) and a **Reviews** disclosure card (`WineDetailView.swift:352`) that actually holds the developer's own tasting notes ("No notes", "N notes").
- **Verified / Unverified** badges render with no explanation (`DetailFormatting.swift`). Authoritative definitions are in `shared/types.ts` (`VerificationState`): *verified* = the shop's live search page rendered and its visible text contains every significant word of the producer; *unverified* = the check could not complete (render failed or timed out, or the wine has no producer recorded); *unchecked* (no badge) = never attempted (K&L's link-only entry, and product pages the reviews module already rendered). **None of the three says anything about vintage or bottling.**
- **Carry-over bug** — PR #42 fixed lists not reloading when a scan's lookups landed, and the detail screen not re-reading the wine. The developer still reported reviews appearing after save but not in the preview. Treat as **not closed** until WI-9's parity check passes.

### WI-1 — Edit a saved wine (web + iOS)

There is no Edit screen after a wine is saved. Add one, reusing the draft form's field components (`WineFieldsSection` on iOS, the shared form on web).

**Fields:** producer, denomination, vintage (blank = NV), region, classification, vineyard, cuvée, colour, **your price (manual)**, **drinking window** (start/end, optional), plus the existing list tags and bottle quantity. **Delete wine** is a destructive button at the bottom (WI-3).

**Your price (manual price) — D12.** Optional single number, labelled "Your price (per 750 ml bottle)", for when the automated lookup was wrong or empty. Never required to save.
- **Storage.** New nullable `wines.manual_price REAL`, added by migration 009 (run-once, checked on a copy of the real database). It is **not** kept in `price_data`, because every price fetch rewrites that blob.
- **Used everywhere.** One helper, `effectivePrice(wine) → { value, basis: 'manual' | 'automated' | null }`: the manual price if set, else `price_data.price_avg`, else null. It lives in `shared/` with a Swift mirror covered by the shared-fixture parity test (§1 D1). Every place that today treats `price_avg` as *the* price goes through it — the list card's price badge, the detail headline, price sorting and filtering, any stats. Find them with a search for `price_avg` / `priceAvg` (web `PriceSection.tsx`, the iOS card and detail, the lines in `routes/wines.ts` that echo it) and list what was routed in the PR.
- **Automated becomes informational.** Detail: the headline reads "Your price $X" with a clear "yours" marker; the automated avg/high/low and the retailer table stay below under **"Retailer prices (automated)"**, visibly distinct. Card: the badge shows your price with the "yours" marker; the automated average is not shown beside it.
- **Never overwritten.** No fetch, refresh or Hard refresh writes `manual_price`. Changing it never triggers the "Refresh searches now?" prompt and never spends credits.
- **Clearing** the field sets NULL and the wine returns to the automated price.
- Positive number, at most two decimals, USD like everywhere else. Drafts (the scan preview) have no manual price; it is an Edit-screen field on saved wines.
- `price_paid` is untouched and still unsurfaced. If the developer later wants purchase-price tracking, that is a separate field.

**Drinking window** — optional. Setting it writes `drinking_window_start/end` with `drinking_window_source = 'manual'`, which Phase 8 already protects from automated overwrite. This is the **primary window** (D2). Clearing it removes the manual value and returns the wine to the derived/critic state. If the wine has a derived window and the developer has not set one, the field is **pre-filled from the derived value** and labelled "from critics". The pre-fill is display only: saving without touching it does **not** convert it to a manual value (that would silently stop future automatic updates).

**Identity change → "Refresh searches now?" (D4).** On save, if any identity field (`producer`, `denomination`, `vintage`, `vineyard`, `cuvee`, `quality_classification`) differs from the stored value **and** the wine has `price_data` or `review_data`:
- **Yes** → run price + reviews with `force=true`. The prompt states the credit estimate (WI-7's constants).
- **No** → keep the old data, and mark it stale: record the identity the data was fetched for **inside the JSON blobs** (`price_data.enriched_for`, `review_data[].enriched_for`, the string `identityOf(wine)` returns — no migration). When it differs from the current identity, both the price and review sections show **"Fetched for a different version of this wine — may not match. Refresh."** A blob without `enriched_for` (everything stored before this phase) is treated as unknown: **no flag**, per the "stored enrichment JSON is older than its types" rule in Phase 12's build log.
- A change to colour, your price, window, tags or quantity never prompts.

**Acceptance:** edit producer on a wine with data → prompt appears; Yes spends credits once and replaces the data; No leaves the data with the stale notice; editing quantity alone never prompts. Set "Your price" on Marcoux → the card and the detail headline show it with the "yours" marker, the automated figures move under "Retailer prices (automated)", Hard refresh leaves it unchanged, and clearing it brings the automated price back.

### WI-2 — Primary vs. informational drinking windows; "Check window"; fourth Ready segment

**Definitions (single backend definition — do not port to Swift):** add a derived field on every wine read, in the same way `latest_tasting_note_date` was added in Phase 12 (computed in the read path, not stored, no migration):

`window_status: 'primary' | 'check' | 'none'`
- `primary` — the wine has a wine-level `drinking_window` (manual, or derived from agreeing critics).
- `check` — no wine-level window, and `review_data` carries **two or more** critic windows that disagree (the situation `derive-wine-level.ts` resolves to `null` today).
- `none` — no wine-level window and no critic window at all.

A single critic's window is, by the existing rule, a derived primary window — it never produces `check`.

**List views (web + iOS):** a `primary` wine shows its window as today. A `check` wine shows a **"Check window"** flag where the window would be. A `none` wine shows nothing. The flag is a list-view element only (D3).

**Ready-to-drink widget:** four segments — **Ready now · Needs more time · Check window · No window**. Counts stay *wines, not bottles*. `Past window` still counts under Ready now (Phase 12 decision). Only a `primary` window can place a wine in Ready now or Needs more time; a `check` wine is **never** guessed at from the per-critic windows. Tapping **Check window** filters the cellar list to those wines.

**Detail view (web + iOS):** two visually distinct groups:
1. **Your window** (when set) or **Window (from critics)** with the Sourced marker (when derived) — the primary window, in the normal text style.
2. **Critic windows (for reference)** — one row per critic with attribution, in a muted style with a "reference only" label. Shown whenever any exist, whether or not a primary window is set, so a manual window never hides what critics said.

**Rules carried forward:** per-critic windows are never blended or averaged (`CLAUDE.md` §15); a manual window is never overwritten by an automated run (Phase 8). The developer may *choose* to blend or to adopt one critic's window — by typing it into Edit — which is a manual value, not a system blend.

**Acceptance:** a wine with two disagreeing critic windows and no manual window shows "Check window" in the list, per-critic rows on detail, and counts under **Check window**; entering a window in Edit moves it to Ready now / Needs more time on next load, the flag disappears, and the critic rows remain as reference.

**UI (web + iOS):**

- Delete is reachable from the Edit screen (WI-1) as well as the existing long-press, so it is discoverable.

**Acceptance:** delete a wine that has a note → wine gone from every list, note still listed under Notes with its original producer/denomination/vintage and "Wine removed"; evaluating that wine later (if re-added) starts a fresh note history.

### WI-10 — Critic score order and the card badge (backend + web + iOS)

**Decision (D13, developer 2026-10-05).** Scores are ordered by trusted-reviewer preference with the wine's own vintage first. This replaces the card's old "highest numeric score" rule and reverses the Phase 11 decision not to prioritise sources.

**The trusted set** is data, not logic: `shared/config/trusted-critics.config.ts`, a plain array of canonical publication names exactly as `CRITIC_KEYWORDS` emits them (same principle as `RETAILER_CONFIG`; adding or removing one is a one-line change). Seed:

```
Burghound, Vinous, Wine Advocate, Decanter, Wine Enthusiast,
Wine Spectator, Tim Atkin, Guía Peñín, Gambero Rosso
```

Sources: the 2026-07-20 list in Phase 6.7 (Burghound, Vinous, Wine Advocate, Decanter, Wine Enthusiast) plus the developer's additions of 2026-10-05. Trust is **by publication**, because `review_data` stores the canonical publication, not the person: William Kelley, Allen Meadows, Neal Martin and Galloni already resolve to Wine Advocate, Burghound and Vinous through `CRITIC_KEYWORDS`. **Not** trusted: James Suckling, Jeb Dunnuck (documented as inflated), and any attribution with `known_publication: false`.

**Order** (computed once, in the backend, beside `window_status`; the clients render the order they are given and never re-sort):

| Tier | Same vintage as the wine? | Trusted? |
|---|---|---|
| 1 | yes | yes |
| 2 | yes | no |
| 3 | no | yes |
| 4 | no | no |

Within a tier: highest score first; ties → `known_publication` first, then source order. **The first item is the badge.** (The developer's steps 1–2 are the head of tier 1; step 3 is tier 3 — reached when the wine's vintage has no trusted score; step 4 is the remainder in descending order. Per the developer's answer, a same-vintage score from a non-trusted source (tier 2) still outranks a trusted score for a different vintage (tier 3).)

**"Same vintage"** compares the entry's `page_vintage` to the wine's `vintage` (D10). A score counts as same-vintage only when the page *states* an equal vintage; for an NV wine, a page with no vintage counts as same. A page with no stated vintage — and every blob stored before `page_vintage` existed — is "vintage not stated": it sorts as not-same, carries no year tag and is not muted (vintage ranks and labels but never rejects; read defensively, per the rule in §6).

**Dedupe.** One entry per publication, **after** classification — keep that publication's highest-ranked score. (Deduping first, as `getDedupedCriticScores` does, would let a 2017 Wine Advocate score hide a 2019 one.)

**Output.** Every wine read carries `critic_summary: { ordered: [{ publication, score, vintage, same_vintage, trusted, tier, known_publication }] }`. The preview screen reads the same field, so it cannot disagree with the saved wine (WI-9).

**Display.**
- *Card:* `96 WA` — the existing abbreviation and dashed-border rules stay; a **muted year tag** (`'18`) when the score's stated vintage is not the wine's; `+N` for the rest. Tapping opens detail at the scores section.
- *Detail and preview:* every score, in this order, grouped under **"Your vintage (2019)"** and **"Other vintages"**, a small **Trusted** marker on trusted sources, each with its vintage (D10). Detail is still never truncated beyond the existing "6, then Show all".

**Rules.** Never averaged, never blended; every score is still stored, attributed and shown on detail. The preference changes order and the badge only. No settings screen to edit the trusted set in this phase (the product-context principle of a user-maintained list is met by config for now). **0 metered calls.**

**Acceptance (2019 wine).** `[Jeb Dunnuck 95 (2019), Burghound 91 (2019), Vinous 93 (2017)]` → badge `91 BH`; order Burghound, Dunnuck, Vinous `'17`. `[Vinous 93 (2017), Jeb Dunnuck 95 (2019)]` → badge `95 JD` (same vintage outranks trusted-other-vintage). `[Vinous 93 (2017), Wine Spectator 92 (2016)]` → badge `93 VN '17`. Wine Advocate 2017 and 2019 both present → the 2019 one is kept. A legacy blob with no `page_vintage` → ordered by trust then score, no year tags. Unit tests cover each tier, NV, unknown vintage, dedupe-after-classify, and tie-breaks.

## 6. Rules carried forward — do not re-litigate

- **Metered enrichment stays user-initiated**, with the existing single exception (scan path, primary tier, once per wine, after the free duplicate check) and the Phase 12 price fetch-once rule. Nothing here adds an automatic call. The Edit prompt (WI-1) and Hard refresh (WI-7) are explicit developer actions that state their cost first.
- **Critic scores and windows are never blended.** The developer may enter a window by hand; the system may not.
- A manual drinking window is never overwritten by an automated run. **Neither is a manual price** (`manual_price`, D12).
- Critic scores are never blended **or averaged**. The card badge and the order follow the developer's trusted set (D13, WI-10) — that is ordering, not blending.
- Additive boolean tags; `promoted_at IS NULL` means draft.
- Tier 2 nulls collapse — no empty rows, no dashes. (WI-4's "why no average" sentence replaces a *row of dashes*; it is not a placeholder.)
- Stored `price_data` / `review_data` may predate any field this phase adds. New code reads every new field defensively.
- Each migration file runs once (PR #45). Migration 008 must be checked against a copy of the real database.
