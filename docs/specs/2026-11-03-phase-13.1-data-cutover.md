# Phase 13.1 — Data cutover: the collection moves to the cloud

> v1 — 2026-11-03. Status: **draft for developer review; not started. Built after Phase 13's WI-4 and WI-6–WI-9.**
> Read alongside `docs/specs/2026-10-10-phase-13-production-deployment.md` (Phase 13), `docs/ops/runbook.md` and `CLAUDE.md` §3 "Phase 13".
> **Origin (developer, 2026-11-03):** the one-time database upload was part of Phase 13 WI-4, which the sequence placed before the deploy pipeline and before any phone can reach the cloud. The developer moved it into its own phase, run once the phones can switch, so the laptop and cloud copies never both take changes.

---

## 1. Goal

Move the developer's collection from the laptop database (`backend/db/wine.db`) to the production app (`malolactic-conversion` on Fly, `/data/wine.db`) **once**. Then both phones and the web app use the cloud copy from that moment on, nothing is lost, and nothing is entered twice.

## 2. Why a separate phase

- **The laptop must stop taking changes the moment the upload starts.** Otherwise the two copies drift apart, and SQLite has no merge.
- **The phones can't use the cloud until a TestFlight build with the production URL and an access key reaches them** (Phase 13 WI-7–WI-9). If the upload ran at WI-4, the developer would either keep using the laptop, so the copies diverge, or go without the phone app for the gap.
- So the upload runs **last**, right before the household switches. Everything before it (backups, deploy pipeline, iOS build) can be built and tested against an empty production database.

## 3. Preconditions (all must hold before step 1 of §5)

1. **Phase 13 WI-4 built:** off-machine backups to Cloudflare R2 are running and a restore drill has been done once; the automatic backup before any schema migration is built.
2. **Phase 13 WI-6 built:** merges to `main` deploy to `malolactic-conversion`; the production machine is `performance-4x` and healthy.
3. **Phase 13 WI-7–WI-9 built:** a TestFlight build with the production URL, Keychain access key and version check is installed on the developer's phone and works against the (empty) production backend.
4. **Production `DEVICE_TOKENS` issued** (developer's iPhone, household iPhone, web), per the runbook.
5. **The import mechanism (§4) is merged and deployed.**

## 4. Work items

**WI-1 — Pending-import on start (small).** The live database cannot be replaced while the server has it open, and a Fly machine cannot be reached by SFTP while stopped. So the import happens at the next start. **It must run in `docker-entrypoint.sh`, before Litestream starts** (amended 2026-11-03 when WI-4 put Litestream in front of the server): replacing the file under a running Litestream would break the backup history. After an import, check in the log that Litestream started a new backup generation for the replaced file. If it didn't, the v0.5 `litestream reset` command is the tool to look at. The same mechanism also puts a point-in-time restore in place (runbook, "Roll back to an earlier moment").
- If `<WINE_DB_PATH>.import` exists at start, then before Litestream or the server opens the database, the start-up step:
  1. renames any current database (and its `-wal`/`-shm`) to `<WINE_DB_PATH>.pre-import-<timestamp>`;
  2. runs `PRAGMA integrity_check` on the import file and refuses (leaving everything in place and logging why) unless it returns `ok`;
  3. moves the import file into place and logs the row counts of `wines`, `tasting_notes` and `app_settings`.
- Migrations then run as usual. Phase 13 WI-4's pre-migration backup covers a migration the laptop copy hasn't had yet.
- An import never overwrites without leaving the previous file beside it. Nothing here runs unless the `.import` file is present.
- Tests: no import file means no change; an import with a failing integrity check is refused; a successful import keeps the old file; WAL siblings are moved together.

**WI-2 — Cutover runbook section.** The steps in §5, written into `docs/ops/runbook.md` as commands the developer runs (or asks Claude to run).

**WI-3 — Verification script.** A local script that prints the same counts from the laptop file and, through the authenticated API, from production (wines including drafts, promoted wines, tasting notes, settings), so step 6 is a comparison of two printed tables rather than a judgement.

## 5. The cutover (WI-2 writes this into the runbook)

1. **Freeze the laptop.** Stop the local backend; nothing (iOS Debug build, web on `localhost`) writes to `wine.db` from here on.
2. **Make the upload copy, WAL included.** Run `sqlite3 backend/db/wine.db ".backup 'cutover-YYYYMMDD.db'"` (spec R7: copying the `.db` alone would lose the WAL), then `PRAGMA integrity_check` on the copy.
3. **Record the laptop counts** (WI-3).
4. **Upload:**
   ```bash
   fly ssh sftp put cutover-YYYYMMDD.db /data/wine.db.import --app malolactic-conversion
   ```
   then `fly machine restart`. The server imports on start (WI-1).
5. **Check the log** for the import line and its counts, and that migrations ran.
6. **Compare counts** (WI-3): laptop and production must match exactly.
7. **Spot-check on the phone and the web app:** three known wines (one with tasting notes, one with critic scores, one with a manual price) look the same as on the laptop.
8. **One real scan over cellular** on the developer's phone, end to end, then the household phone's first scan (Phase 13 WI-10).
9. **Keep the laptop file** (`wine.db` and `cutover-YYYYMMDD.db`) untouched until the developer signs off (Phase 13 WI-4's rule). After sign-off, local development uses a copy, never the original.

**Rollback:**
- Before anyone has written to the cloud copy, rollback is "keep using the laptop": it was frozen and unchanged.
- After writes, roll back by restoring from R2 (Phase 13 WI-4).
- The `.pre-import-<timestamp>` file on the volume is the production state just before the import.

## 6. Cost

No new metered call. One machine restart. The upload is a few megabytes.

## 7. Acceptance criteria

1. Counts of wines (including drafts), promoted wines, tasting notes and settings match between the frozen laptop copy and production.
2. Both phones and the web app show the collection from the cloud, over cellular and Wi-Fi, with the laptop backend stopped.
3. A scan on each phone after cutover saves to the cloud copy and appears on the other phone.
4. The laptop original and the cutover copy are kept until sign-off.

## 8. Out of scope

Two-way sync or merging changes made on both sides; keeping the laptop as a live second copy; importing other databases; a scheduled re-import.

## 9. Open questions

1. **Cutover date:** the developer picks it once preconditions 1–5 hold. It should be a quiet moment, since the laptop is frozen from step 1.
2. **Drafts:** they are imported as-is. The 24-hour sweep removes stale ones on the next start, as it does on the laptop.
